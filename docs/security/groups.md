# Группы отдельно от root — фаза 1

**Статус:** реализовано в `feat/root-groups` (фаза 1). Это базовая групповая
модель: дополнительные группы процесса, групповые проверки VFS, групповые
устройства `/dev`, минимальная база `/etc/passwd` + `/etc/group` и команды
`id`/`groups`/`su` **без пароля**. Логин, setuid-бинари и capabilities — фаза 2
(§7); до неё эта страница — контракт того, что есть, и того, чего намеренно нет.

Не читайте фазу 1 как многопользовательскую границу безопасности: единственный
пользователь, способный войти за консоль, — root (shell — kernel-код), а
непривилегированная сессия получается только явным `su` из root-сессии.

## 1. Модель

### 1.1 Креденшелы и дополнительные группы

`src/arch/x86_64/linux/cred.rs` (чистый `core`-модуль, host-свойства P56/P58):

```rust
pub const GROUPS_CAP: usize = 32;

pub struct Creds {
    pub uid, gid, euid, egid, suid, sgid: u32,
    groups: [u32; GROUPS_CAP],  // первые ngroups значимы
    ngroups: usize,
}
```

* `Creds::ROOT` — идентичность каждого процесса, порождённого ядром; набор
  дополнительных групп пуст.
* Дополнительные группы — часть `CompatState::creds`, поэтому `fork`/`clone`
  копируют их, а `execve` сохраняет (setuid-бинари не моделируются).
* `Creds::in_group(gid)` истинно, когда `gid == egid` **или** `gid` есть в
  дополнительном наборе. Real `gid` сам по себе группового класса не даёт:
  Linux решает по effective id, а `setgroups(2)` меняет общий набор.
* Cap 32 вместо Linux `NGROUPS_MAX = 65536` — осознанное ограничение `no_std`
  ядра с фиксированной кучей: `Creds` — `Copy`-снимок, который копируется на
  каждом fork и каждой проверке прав. `setgroups(2)` с большим `size`
  отвергается `EINVAL`, а не обрезается молча.

### 1.2 Проверки прав

`Creds::may(mode, (owner_uid, owner_gid), access)` — та же POSIX-матрица, что
была до фазы 1, с одним расширением:

1. класс выбирается так: `euid == owner_uid` → owner; иначе
   `owner_gid` равен `egid` **или** любому дополнительному gid → group; иначе
   other;
2. внутри класса разрешает ровно соответствующий бит `r`/`w`/`x`;
3. **root** (`euid == 0`) обходит чтение и запись, но не исполнение: для `x`
   нужен хотя бы один из битов `0o111`. Это правило не менялось и не
   ослаблялось.

`access(2)`/`faccessat(2)` проверяют **real** ids: `Creds::with_real_ids()`
проецирует `euid := uid`, `egid := gid`, но **сохраняет дополнительные
группы** — иначе group-класс `access()` перестал бы видеть собственные группы
процесса.

### 1.3 Сисколлы `getgroups(2)` / `setgroups(2)`

x86_64 nr **115/116** (`src/arch/x86_64/linux/abi.rs`, ветки диспетчера,
независимый `EXPECTED`-список).

| вызов | контракт pagh |
|---|---|
| `getgroups(0, NULL)` | вернуть число дополнительных групп; `list` не читается |
| `getgroups(size < n, list)` | `EINVAL` (Linux), указатель не проверяется |
| `getgroups(size >= n, list)` | записать ровно `n` gid'ов; `list` проверяется на запись до первой записи → `EFAULT`, частичный результат ненаблюдаем |
| `setgroups(0, NULL)` | очистить набор (root) |
| `setgroups(size > cap, list)` | `EINVAL` до чтения массива |
| `setgroups(..., list)` непривилегированный | `EPERM` до любой работы (`CAP_SETGID` сведён к `euid == 0`) |
| `setgroups(..., list)` root | прочитать `size` gid'ов (`EFAULT` на плохом указателе), заменить набор; `gid 0` разрешён, как в Linux с `CAP_SETGID` |

`setgroups` меняет только дополнительные группы: `uid`/`gid`/`euid`/`egid`/
`suid`/`sgid` не трогаются. Проверено host-свойством P56 (cap, EPERM/EINVAL по
построению, сохранение ids), in-QEMU routine
`security::get/set*id syscall round-trip` (счётчик/размер/указатель) и e2e
`tools/e2e.py groups` реальной статической гостевой программой.

## 2. Идентичности: `/etc/passwd` и `/etc/group`

`src/provision.rs` идемпотентно устанавливает минимальную базу **и на уже
провижиненном диске** (обновление ядра не требует переформатирования;
`write_once` никогда не перезаписывает пользовательские правки):

`/etc/passwd`:

```text
root:x:0:0:root:/root:/bin/sh
oleg:x:1000:1000:Oleg:/home/oleg:/bin/sh
```

`/etc/group`:

```text
root:x:0:
tty:x:5:oleg
disk:x:6:
wheel:x:10:
video:x:44:oleg
net:x:90:
input:x:105:oleg
oleg:x:1000:
```

| gid | группа | смысл в pagh |
|---|---|---|
| 0 | `root` | владелец системных файлов и узлов |
| 5 | `tty` | терминальная сессия: `/dev/vtconsole0` |
| 6 | `disk` | сырые блочные устройства (фаза 2; сейчас прав не даёт) |
| 10 | `wheel` | администраторы (фаза 2: `su`/login) |
| 44 | `video` | `/dev/fb0` — экран |
| 90 | `net` | сетевое администрирование (фаза 2; прав не даёт) |
| 105 | `input` | `/dev/input/event0`, `/dev/vtinput` — клавиатура/мышь |
| 1000 | `oleg` | основной пользователь desktop-варианта |

Номера `tty/disk/wheel/video/input` совпадают с распространёнными
Debian-подобными значениями; `net = 90` — исторический номер группы `net`,
зарезервированный pagh. Домашний каталог `/home/oleg` создаётся с владельцем
`1000:1000` и режимом `0755` **только при создании** (существующий каталог
boot-путь не перештамповывает).

`id`/`groups`/`su` разбирают **те же** файлы чистыми функциями
`src/shell/identity_db.rs` (host-свойство P58): семь полей passwd, четыре поля
group, `#`-комментарии и NIS-строки пропускаются, кривая строка не роняет
загрузку. Поиск — первое совпадение, как `getpwnam(3)`.

## 3. Устройства `/dev`

| узел | владелец | режим | почему |
|---|---|---|---|
| `/dev/fb0` | `root:video` | `0660` | экран: чтение кадра = чтение секретов на экране |
| `/dev/input/event0` | `root:input` | `0660` | поток клавиатуры/мыши = кейлоггер |
| `/dev/vtconsole0` | `root:tty` | `0660` | shared VT surface: содержимое консоли |
| `/dev/vtinput` | `root:input` | `0660` | приём VT-байтов (ввод терминала) |
| `/dev/null`, `/dev/zero`, `/dev/full` | `root:root` | `0666` | не ресурсы: сток/нули/тест ошибки записи; доступность не должна зависеть от идентичности |
| `/dev/serial` | `root:root` | `0644` (историческое) | диагностический serial; не менялся в фазе 1 |

`/dev/zero` и `/dev/full` добавлены в фазе 1 (Linux-контракт): `zero` читает
нули и отбрасывает запись, `full` читает нули и отвергает запись `ENOSPC`.

Групповые биты проверяются слоем сисколлов на `open`/`read`/`write`/`mmap`, как
и любые другие метаданные VFS. Композитор (desktop-вариант B) должен быть
**единственным** держателем `fb0`/`event0`/`vtconsole0`: у группы `video`/`input`
нет способа отличить его от любого другого процесса с теми же группами, поэтому
эксклюзивность — политика композитора и сессии, а не enforcement ядра (см. §5).

## 4. Shell: `id`, `groups`, `su`

* `id [user]` — без аргумента: `uid=…(…), gid=…(…), groups=…` сессионной
  идентичности; с аргументом — запись `/etc/passwd` и её группы из
  `/etc/group`. Формат повторяет coreutils.
* `groups [user]` — имена групп через пробел, основная группа первой, затем
  явные членства из `/etc/group`.
* `su [user]` — **только root-сессия**; цель — `root` (сброс) или `oleg`
  (uid 1000). Пароля нет. Выход:

  ```text
  su: no password authentication in phase 1: root -> oleg (uid=1000 gid=1000)
  su: groups=1000(oleg),5(tty),44(video),105(input)
  su: 'lxrun' now starts programs with these credentials; shell built-ins still
      run as kernel/root (phase-1 limitation)
  ```

  Смена **односторонняя**: из непривилегированной сессии `su root` — `EPERM`
  (иначе отсутствие пароля было бы эскалацией). Вернуться к root можно только
  перезагрузкой.

### Как `su` влияет на процессы

Shell хранит сессионные креденшелы (`src/shell/identity.rs`), а `lxrun` вызывает
`process::run_linux_binary_as(creds, …)`: ребёнок получает эти креденшелы в
своём `CompatState`, и дальше все проверки слоя сисколлов применяются к нему
обычным путём. Для не-root сессии лаунчер проверяет **read+execute** финального
образа по тем же битам, что `execve`; root-сессия сохраняет историческое
поведение kernel-лаунчера (обходит проверку сисколлов, как описано в
`SECURITY.md`).

**Чего `su` не делает:** встроенные команды shell (`cat`, `ls`, `write`, `pkg`,
`nano`, …) — kernel-код и исполняются с привилегиями ring 0 независимо от
сессии; VFS по-прежнему не знает вызывающего (это архитектурный инвариант
`AGENTS.md` §11, необходимый boot-провижинингу и установщику пакетов). Поэтому
`su` — честное понижение **процессов**, но не граница безопасности shell. Это
главное ограничение фазы 1.

## 5. Threat model

### Активы

* **Экран** (`fb0`, `vtconsole0`): содержимое консоли/композитора может включать
  секреты (вывод команд, редактор, будущий менеджер паролей).
* **Ввод** (`event0`, `vtinput`): нажатия клавиш — пароли, команды, переписка.
* **Целостность сессии**: кто может сменить идентичность, тот может читать
  чужие файлы.
* **Raw-устройства** (`disk`) и сеть (`net`) — пока зарезервированы, но номера
  групп уже выделены, чтобы фаза 2 не переизобретала их.

### Доверенные и недоверенные

* **Доверен:** root (единственный способ войти за консоль в фазе 1) и код ядра.
* **Не доверен:** любой процесс с `uid 1000`, включая программы, запущенные
  через `lxrun` после `su oleg`, и Linux-userland, установленный из пакетов.
* **Граница доверия — членство в группе.** `video`/`input` дают ровно то, что
  обещают: чтение экрана/ввода. Процесс в `input` неотличим от композитора по
  правам на устройство; «композитор — единственный владелец» держится на том,
  что в этих группах больше никого нет и приложение не получает группу
  случайно. Это политика сессии/пакета, а не мандат ядра.

### Что фаза 1 защищает

* Непривилегированный процесс (uid 1000) **не** открывает `fb0`/`event0`/
  `vtconsole0`/`vtinput`, если он не в соответствующей группе; root — открывает.
* Group-биты VFS работают для **любого** дополнительного gid, не только `egid`:
  файл `root:video 0640` читается членом `video` и не читается остальными.
* `setgroups` не может расширить набор непривилегированному процессу: он
  `EPERM` до чтения массива.
* `su oleg` не даёт способа вернуться к root без перезагрузки.
* Root-bypass не ослаблен: root по-прежнему обходит r/w, но не execute.

### Чего фаза 1 **не** защищает (честно)

* **Нет аутентификации.** `su` не спрашивает пароль: любой, кто уже за
  root-консолью, и так root. Пароли/`/etc/shadow`/login — фаза 2. Не
  используйте `su` как «вход в систему».
* **Нет setuid-бинарей и capabilities.** `execve` никогда не меняет ids;
  повышения прав через файл нет. `chown`/`chmod` остаются root-или-владелец,
  как раньше.
* **Нет login/session manager.** Один console-shell; нет `getty`, нет
  per-user сессий, нет `utmp`.
* **`su` не понижает сам shell** (см. §4): встроенные команды остаются root.
* **Корректность search-битов у `lxrun` (фаза 2, агент B):** для не-root
  сессии `run_linux_binary_as` разрешает путь проверяющим обходчиком
  (`lookup_path_walk_checked` с `may_search` по креденшелам ребёнка) и затем
  требует read+execute на финальном образе, поэтому промежуточный каталог без
  `x` даёт `EACCES`. `execve(2)` идёт тем же checked-обходом при загрузке
  образа. `EACCES` на промежуточном каталоге покрыт host-свойством
  `link_walk_paths`; непроверяемым остаётся только намеренно привилегированный
  kernel-лаунчер `run_linux_binary` (boot-selftest'ы).
* **Нет per-seat/DRM-master.** Эксклюзивность `fb0` — соглашение, а не
  enforcement; любой член `video` может открыть экран параллельно.
* **Нет ACL, audit trail, `fsuid`/`fsgid`, user namespaces.** Набор групп — это
  вся групповая модель.
* **`Cap 32`** (против 65536 в Linux) — осознанное ограничение.
* **Компромисс ядра или root-процесса** — вне модели.

## 6. Тесты и доказательства

* Host property **P56** (`host-tests/src/properties/p56.rs`): oracle `may` с
  дополнительными группами, `setgroups` (EPERM/EINVAL/cap/ids неизменны),
  сохранение групп в real-id-проекции `access()`. Inline unit-тесты `cred.rs`.
* Host property **P58** (`host-tests/src/properties/p58.rs`): round-trip
  `/etc/passwd`/`/etc/group`, `groups_for_user`/`supplementary_*` против
  независимого oracle, first-match, произвольный текст не паникует.
* In-QEMU `selftest` (routine'ы `security::*`):
  `device nodes carry group modes + supplementary-gid checks`,
  `/etc/passwd + /etc/group parse into ids and groups`,
  `fork/clone inherit supplementary groups`,
  плюс расширенный `get/set*id syscall round-trip`.
* E2E `python3 tools/e2e.py groups`: собирает статический probe
  (`tools/group_probe.c`), кладёт его в scratch-ext2 и проверяет **реальными
  сисколлами из ring 3**: `getgroups`/`setgroups` (root и uid 1000), групповой
  `open` файла `root:video 0640`, `fb0`/`vtconsole0`/`null`, `EPERM`
  непривилегированного `setgroups`, наследование групп через `su oleg` +
  `lxrun` (probe печатает свои ids/groups уже как uid 1000).

## 7. Roadmap фазы 2

1. **Login/password.** `/etc/shadow` (или хэш в отдельном файле), `crypt`
   (наш код; никакого GPL), `login`/`getty`-эквивалент, PAM-подобный минимум:
   аутентификация → `setgroups` → `setgid` → `setuid` → `exec` shell. Только
   после этого `su` станет настоящим входом, а не переключением сессии.
2. **Setuid/setgid-бинари.** `execve` читает `S_ISUID`/`S_ISGID` под
   `nosuid`-политикой монтирования, выставляет `euid`/`egid`/saved ids и
   сбрасывает дополнительные группы для setuid-root; аудит всех путей
   (symlink, `O_PATH`, `execveat`). До этого — запрет на установку таких битов
   из пакетов.
3. **Capabilities.** Разложить root-модель на минимальные наборы:
   `CAP_DAC_OVERRIDE`/`CAP_DAC_READ_SEARCH` (root bypass), `CAP_SETGID`/
   `CAP_SETUID`, `CAP_CHOWN`/`CAP_FOWNER`, `CAP_SYS_TTY_CONFIG`. `wheel` (gid 10)
   становится группой администраторов, но не заменой capability-проверок.
4. **Устройства и места.** Per-seat группы, передача `fb0` композитору с
   эксклюзивностью (DRM-master-подобный handoff), `disk` — только для
   `pkg`/`mount`-подобных операций, `net` — для сетевой настройки.
5. **Политика и аудит.** `login.defs`-аналог, запрет пустых паролей,
   блокировка после N попыток, audit-лог смены идентичности, `su` в `wheel`
   (сейчас разрешён только root-сессии).
6. **Пробелы, которые не входят в фазу 2:** ACL, NFSv4 ACL, user namespaces,
   SELinux/AppArmor, seccomp — отдельные проекты, не блокирующие login/setuid.

Пока фаза 2 не готова, `su` без пароля остаётся **документированным
ограничением**, а не забытой проверкой: смотрите текст, который печатает сама
команда, и этот документ.
