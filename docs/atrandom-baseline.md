# Issue #16 (AT_RANDOM) — БАЗА ДЕФЕКТА на старом коде (main `cd542bb`)

Роль: независимая верификация t11 (исполнитель — dima-net, ветка `arch/at-random-entropy`).
Это доказательство «ДО»: без него фикс недоказуем. Собственный worktree:
`/home/oleg/pagh-wt-atrandom-base`, ветка `verify/atrandom-baseline`, база — main `cd542bb`.
Проба (`src/arch/x86_64/linux/misc.rs` + shell-команда `atrand`) **только логирует**
входы/выход существующей функции; арифметика не изменена (входы вынесены в локалы в том же
порядке чтения). Ветка — инструмент верификации, не для мержа.

## 1. Что именно деградирует без RDSEED/RDRAND

`misc::random_bytes_16()` (`src/arch/x86_64/linux/misc.rs:178-198`) сначала пытается взять
аппаратную энтропию (`security::entropy::fill` → RDSEED, затем RDRAND). На `-cpu qemu64` обеих
инструкций нет (`capabilities_str()` → `none`), `secure_u64()` возвращает `Err`, и блок
собирается fallback-ветвью:

```rust
static FALLBACK_STATE: Spinlock<u64> = Spinlock::new(0x9E37_79B9_7F4A_7C15);  // публичная константа
let mut x = *FALLBACK_STATE
    ^ scheduler::ticks().wrapping_mul(0x9E37_79B9_7F4A_7C15)
    ^ (rtc::now_unix() as u64).rotate_left(32)
    ^ scheduler::current_pid() << 48
    ^ crate::security::entropy::secure_u64().unwrap_or(0);   // == 0 без RDSEED/RDRAND
x ^= x << 13; x ^= x >> 7; x ^= x << 17;                     // детерминированный микшер
*g = x;                                                       // ПЕРСИСТЕНТНОЕ глобальное состояние
out[..8]  = x.to_le_bytes();
out[8..]  = (x.wrapping_mul(0xBF58_476D_1CE4_E5B9)).to_le_bytes();
```

Существенное: комментарий обещает «a free-running process-lifetime counter», которого в коде
**нет** — вместо него `secure_u64().unwrap_or(0)`, то есть ровно ноль там, где fallback и
включается. Единственный непубличный вход — предыдущее значение `FALLBACK_STATE`, а оно на
первом вызове равно публичной константе.

## 2. Наблюдаемость входов (пункт 1 капитана)

| Вход | Как наблюдаем снаружи | Точность |
|---|---|---|
| `scheduler::ticks()` | `clock_gettime(CLOCK_MONOTONIC)` → `ticks_to_timespec(ticks, …, TICK_HZ)` (`misc.rs:136`); в моём срезе procfs ещё и `/proc/uptime` (2 знака = 10 мс); shell `uptime` печатает ticks | ±1 tick (MONOTONIC), ±5 ticks (/proc/uptime) |
| `rtc::now_unix()` | `clock_gettime(CLOCK_REALTIME)` → `rtc::now_unix()` (`misc.rs:139-141`) | точно (секунда) |
| `current_pid()` | `getpid(2)`; для следующего процесса pid предсказуем (монотонный счётчик) | точно |
| `FALLBACK_STATE` | на **первом** вызове — публичная константа `0x9E3779B97F4A7C15`; далее — предыдущий `x`, который вычисляется из тех же публичных входов | точно после одной итерации |
| `secure_u64().unwrap_or(0)` | CPUID: нет RDSEED/RDRAND ⇒ 0 (в моём срезе видно и в `/proc/cpuinfo: flags`) | точно |

Вывод: **ни одного секрета во входах нет**. Все пять слагаемых либо читаются unprivileged
процессом на той же машине, либо равны публичной константе.

## 3. Прогон (QEMU, `-cpu qemu64`, без RDSEED/RDRAND)

Команда: `python3 tools/e2e.py shell --cpu qemu64 --cmd 'uptime' --cmd 'atrand 8'`
(канонический лог этого прогона — `/tmp/atrandom/qemu64.log`; сохранён копией из worktree).

```
[atrand] hw=none state_in=9e3779b97f4a7c15 ticks=5675 rtc=1789662875 pid=1 hw_term=0x0 \
         bytes=a130cea17b6f18de5929e54a972cd015
[atrand] hw=none state_in=4bc9dec9b6071e4f ticks=5677 rtc=1789662875 pid=1 hw_term=0x0 \
         bytes=…(8 сэмплов подряд; state_in каждого следующего = x предыдущего)
… (8 сэмплов подряд; state_in каждого следующего = 8 байт предыдущего)
```

### 3.1 Детерминизм: блок воспроизводится хост-моделью из публичных входов

Хост-модель `/tmp/atrandom/model.py` переписывает ту же арифметику и **побайтово совпадает со
всеми 8 блоками** ядра (`DETERMINISM: model reproduces every block (no secret)`), причём
состояние модели совпадает с залогированным `state_in` каждой итерации. То есть AT_RANDOM —
детерминированная функция публичных входов, а не случайная величина.

### 3.2 Восстановление seed'а перебором

Атакующий, знающий RTC-секунду и pid и имеющий лишь окно по ticks (например, знание времени
загрузки ±2 c):

```
window ±2000 ticks -> 4001 guesses, seed found at ticks=5675 (true=5675)   # знание времени загрузки ±2 c
window ±5    ticks ->   11 guesses                                        # точность /proc/uptime (0.01 c)
window ±1    tick  ->    3 guesses                                        # точность CLOCK_MONOTONIC
window ±0          ->    1 guess  (hit at ticks=5675)                      # co-located: читаем часы сами
recovered block from public inputs: a130cea17b6f18de5929e54a972cd015
```

Одного попадания достаточно, чтобы предсказать **всю дальнейшую последовательность** (8/8
блоков воспроизведены моделью из (ticks, rtc, pid) без наблюдения самих блоков) — состояние
глобальное и персистентное, поэтому восстановление seed'а на первой же загрузке раскрывает
ключи всех последующих процессов.

### 3.3 Половина блока — производная, а не энтропия

`bytes[8:16] == (bytes[0:8] * 0xBF58_476D_1CE4_E5B9)` подтверждено на наблюдаемом блоке:
вторая половина выводится из первой, независимой энтропии в ней нет (блок несёт 64 бита).

### 3.4 «NEVER degrades to all-zero bytes» не обеспечивается кодом

Ноль достигается тогда и только тогда, когда pre-xorshift значение равно 0 (xorshift(0) = 0),
то есть при `ticks = (state ^ rotl(rtc,32) ^ (pid<<48) ^ hw_term) * K^{-1} mod 2^64`
(`K` нечётный, обратим). Для наблюдаемого сэмпла это `ticks=9539086926640840705` — в
практике недостижимо (not reachable in practice), но это **удача, а не инвариант**: в коде
нет ветки, гарантирующей ненулевой блок.

### 3.5 Контроль: с аппаратной энтропией путь другой

`python3 tools/e2e.py shell --cpu max --cmd 'atrand 3'` (лог `/tmp/atrandom/cpu-max.log`):
`ATRAND start … hw_avail=true hw=rdseed+rdrand`, и **ни одной** строки `[atrand] hw=none` —
fallback не исполнялся. Три полученных блока моделью из публичных входов **не
воспроизводятся** (отрицательный контроль к 3.1).

## 4. Почему это дефект, а не косметика

glibc использует `AT_RANDOM` как ключ stack-canary и pointer-mangling (в самом комментарии
к функции это и написано). Предсказуемый ключ = известный canary: утечка одного байта стека
превращается в контроль потока, а после восстановления seed'а становятся известны ключи всех
последующих процессов той же загрузки.

## 5. Что должно измениться в «ПОСЛЕ» (критерии приёмки t11)

1. При `-cpu qemu64` fallback больше **не** воспроизводится моделью из (ticks, rtc, pid):
   перебор по окну (и даже точное знание входов) не даёт блок.
2. Два вызова подряд при одинаковых наблюдаемых входах дают разные блоки (то есть в микшер
   добавлен источник, недоступный наблюдателю).
3. Отрицательные контроли: блок не константа, не ноль, вторая половина не выводится из первой
   детерминированной функцией того же вида.
4. Путь с `-cpu max` не изменился: fallback не вызывается, `hw_avail=true`, число
   `unnecessary unsafe` варнингов в `src/security/entropy.rs` уменьшилось (в базе t2 их 4),
   host-tests зелёные, остальные гейты — как в базе t2.
5. Host-свойства микшера — не тавтологичны (см. чек-лист §6).

## 6. Аудит host-свойств на тавтологичность (чек-лист для t11)

Свойство ничего не доказывает, если оно выполняется при любом входе или не различает
сломанный микшер. По каждому свойству dima-net нужно показать:

| Вопрос | Что проверяю |
|---|---|
| Что варьируется на входе? | есть ли `proptest`-стратегия по seed/состоянию, а не один фиксированный вектор |
| Ломается ли свойство, если микшер вырождается в константу? | мысленный/машинный мутант: `mix(seed) = C` — свойство должно падать |
| Ломается ли оно, если убрать один вход (например, ticks)? | мутант `mix = f(seed)` без счётчика — свойство должно падать |
| Проверяется ли *связь* вход→выход, а не только форма? | «длина 16», «не все нули», «два вызова различаются» сами по себе тавтологичны и не годятся как единственные |
| Есть ли отрицательный контроль? | тест, который на СТАРОМ микшере обязан падать (иначе свойство не различает дефект) |

Проверяемые формулировки, которые я считаю не-тавтологичными: (а) детерминизм при
фиксированном секрете и разных публичных входах; (б) различие выходов при одинаковых
публичных входах и разных секретах; (в) отсутствие воспроизводимости моделью по публичным
входам (свойство-«атака»); (г) битовая лавина/лавинный критерий (изменение одного бита входа
меняет ≥ половины бит выхода) — но её надо предъявлять как статистику с порогом, а не как
«выходы различаются».
