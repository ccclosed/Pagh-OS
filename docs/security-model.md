# Модель безопасности: учётные данные процессов и права файловой системы

**Статус:** реализовано. По умолчанию всё работает от root, поэтому существующий userland (shell, apt, CPython) продолжает работать без изменений; новое поведение проверяется in-QEMU набором selftest и host-свойством P56.

Эта страница — контракт. Она говорит, что именно проверяется, где и что сознательно не моделируется. Не читайте её как заявление о sandboxing или многопользовательской безопасности.

## 1. Учётные данные

`src/arch/x86_64/linux/cred.rs` (чистый модуль, только `core`, host-свойство P56) определяет:

```rust
pub struct Creds {
    uid, gid, euid, egid, suid, sgid: u32,
    groups: [u32; GROUPS_CAP],   // дополнительные группы, GROUPS_CAP = 32
    ngroups: usize,
}
pub enum Access { Read, Write, Execute }
```

* `Creds::ROOT` — идентичность каждого процесса, порождённого ядром.
* Учётные данные хранятся в `CompatState::creds` (`src/task/compat.rs`), а не в VFS или планировщике. `fork`/`clone` наследуют значение целиком (включая дополнительные группы); `execve` его сохраняет (setuid-бинарники не моделируются, поэтому exec никогда не повышает и не сбрасывает ids). Нативная задача pagh без `CompatState` сообщает сисколл-слою `Creds::ROOT`.
* Аксессоры для сисколлов: `compat::current_creds`, `set_current_creds`, `creds_of`.
* **Дополнительные группы** (фаза 1 «группы отдельно от root») — `Creds::setgroups`/`with_groups`, до `GROUPS_CAP = 32` gid'ов; `getgroups(2)` (115) и `setgroups(2)` (116) — в `misc.rs`, детали и threat model — `docs/security/groups.md`. `setgroups` разрешён только `euid == 0` (модель `CAP_SETGID`), `size > cap` — `EINVAL`; gid 0 разрешён. `fsuid`/`fsgid` по-прежнему не моделируются.

### `may`: POSIX-матрица

`Creds::may(mode, (owner_uid, owner_gid), access)`:

1. эффективные ids выбирают класс: `euid == owner_uid` → биты владельца, иначе `owner_gid == egid` **или** `owner_gid` входит в дополнительные группы → биты группы, иначе биты остальных;
2. класс разрешает доступ тогда и только тогда, когда его три бита содержат запрос;
3. **root** (`euid == 0`) обходит чтение и запись, но не исполнение: execute разрешён тогда и только тогда, когда хотя бы один из девяти битов прав — бит исполнения (`mode & 0o111 != 0`).

Участвуют только младшие девять битов прав; биты типа и setuid/setgid/sticky маскируются. Групповой класс — единственное расширение фазы 1: он выбирается по `egid` или любому дополнительному gid, а не только по `egid`. `fsuid`/`fsgid` нет. `access(2)`/`faccessat(2)` проверяют real ids (`Creds::with_real_ids()`), но **сохраняют** дополнительные группы — иначе group-класс `access()` не видел бы собственные группы процесса.

### Переходы `set*id`

`setuid`/`setgid`, `setreuid`/`setregid`, `setresuid`/`setresgid` реализованы в том же чистом модуле и следуют правилам владения Linux:

| вызов | root (`euid == 0`) | иначе |
|---|---|---|
| `setuid(x)` | все три UID := x | x должен быть real или saved; `euid := x`, `suid := x`, real не меняется |
| `setgid(x)` | все три GID := x | x должен быть real или saved; та же форма |
| `setreuid(r, e)` | тот, что не `-1` | `r ∈ {uid, suid}`, `e ∈ {uid, euid, suid}`; saved следует за новым эффективным id, если переход был запрошен |
| `setresuid(r, e, s)` | тот, что не `-1` | каждое указанное значение ∈ `{uid, euid, suid}` |
| `setre[ug]id(-1, -1)` | no-op | no-op |

`setres[ug]id` никогда не выдумывает идентичность для непривилегированного вызывающего; `setuid`/`setgid` на непривилегированном пути никогда не меняют real id. Отвергнутый переход возвращает `EPERM`. `getresuid`/`getresgid` проверяют все три пользовательских указателя, прежде чем писать хоть один.

Одно сознательное отклонение от Linux: на непривилегированном пути `setuid`/`setgid` pagh также выставляет saved id в новый эффективный id, поэтому процесс, сбросивший root, не может вернуть его через saved id. Это строже Linux (который saved id не трогает) и является правилом, которого требует эта модель; это не обещание совместимости для setuid-root программ, которые pagh всё равно не поддерживает.

`getgroups(2)` возвращает число дополнительных групп (`size == 0` — только счётчик), `EINVAL` при `size < n`, пишет ровно `n` gid'ов после проверки всего диапазона на запись (`EFAULT` до первой записи). `setgroups(2)` — только `euid == 0` (`EPERM` иначе, до чтения массива), `size > 32` — `EINVAL`, `size == 0` очищает набор. Идентичности `uid`/`gid`/`euid`/`egid`/`suid`/`sgid` при этом не меняются.

## 2. Метаданные файловой системы

`VfsNode` (`src/vfs/mod.rs`) получил четыре **только-метаданные** метода:

| метод | по умолчанию | ext2 |
|---|---|---|
| `mode() -> u32` | `0o755` каталог / `0o644` файл | `i_mode & 0o7777` |
| `owner() -> (u32, u32)` | `(0, 0)` | `(i_uid, i_gid)` |
| `set_mode(u32)` | `NotSupported` | журналируемая запись `i_mode`, биты типа сохраняются |
| `set_owner(u32, u32)` | `NotSupported` | журналируемая запись `i_uid`/`i_gid`; значения > `u16::MAX` — `EINVAL` |

VFS никогда не проверяет учётные данные. Провижининг при загрузке, установщик пакетов и shell вызывают эти методы напрямую, ровно как раньше. `MountNode` пробрасывает все четыре. Создание через сисколл проставляет создателю `euid`/`egid` на новом узле (`stamp_creation_owner`), потому что писатель ext2 не имеет учётных данных и всегда хранит `(0, 0)`; собственные `(0, 0)` root не требуют лишней транзакции. Синтетические узлы `/dev` и `/proc` по-прежнему владельца не хранят; ramfs (`/tmp`) с фазы 2 хранит `mode` и `owner` на узле, поэтому созданный не-root файл принадлежит ему — без этого sticky-правило `/tmp` не смогло бы отличить свой файл от чужого.

## 3. Точки проверки (только слой сисколлов)

Все проверки живут в `src/arch/x86_64/linux/`; VFS остаётся свободен от учётных данных.

| операция | правило | errno |
|---|---|---|
| обход пути (каждый обработчик, резолвящий путь) | search (`x`) на каждом промежуточном каталоге, эффективные ids (у `access(2)` — его real ids); компоненты, вставленные из цели разыменованной symlink, тоже проверяются | `EACCES` |
| `open`/`openat` существующего узла | чтение для `O_RDONLY`; запись для `O_WRONLY`/`O_RDWR`; оба для `O_RDWR`; запись дополнительно для `O_TRUNC` (проверяется до усечения) | `EACCES` |
| `open`/`openat` `O_CREAT` | запись **и** исполнение на родительском каталоге | `EACCES` |
| `execve` | исполнение на цели; root всё равно нуждается в одном x-бите | `EACCES` |
| `unlink`/`rmdir`/`mkdir` | запись+исполнение на родительском каталоге; для удаляемой записи дополнительно sticky-правило (`S_ISVTX`) | `EACCES`, sticky — `EPERM` |
| `rename`/`renameat`/`renameat2` | запись+исполнение на исходном **и** целевом родителях, обе проверки до любой мутации; sticky-правило для источника и (если приёмник существует) для заменяемой записи | `EACCES`, sticky — `EPERM` |
| `chmod`/`fchmod` | root или владелец inode | `EPERM` |
| `chown`/`fchown` | только root; `(uid_t)-1` сохраняет текущий id | `EPERM` |
| `kill` | euid отправителя — root или совпадает с real/effective uid цели; групповой/широковещательный send доставляет разрешённому подмножеству | `EPERM`, если не разрешён никто |
| `tgkill` | то же правило для адресованного потока | `EPERM` |
| `access` | real-id-вариант матрицы `may` (`R_OK`/`W_OK`/`X_OK`; `F_OK` — существование); разыменовывает symlink; проверка обхода использует те же real ids | `EACCES` |
| `chdir` | поиск (`x`) на самом целевом каталоге, а также на каждом промежуточном | `EACCES` |
| `stat`/`lstat`/`fstat` | сообщает реальные биты прав inode, тип и `st_uid`/`st_gid` (per-process override — только для узлов, которые не могут хранить метаданные) | — |

Разрешение на поиск в каталоге проверяется внутри **чистого обходчика ссылок** (`vfs::link_walk`): перед каждым поиском имени обходчик спрашивает у своего адаптера `LinkTree` `may_search`, а адаптер сисколл-слоя (`io_sys::walk_as`) отвечает `Creds::may(node.mode(), node.owner(), Access::Execute)` для эффективных ids. Это покрывает каждый компонент, через который проходит путь сисколла, — включая компоненты, которые вставляет в обход разыменованная символьная ссылка, а префиксная проверка по записанному пути их бы пропустила, — при этом права самого финального компонента остаются заботой сисколла (`open` нужны чтение/запись, `stat` — ничего). `lstat`/`readlink` сохраняют семантику без разыменования: search требуется на каталогах, через которые они проходят, но не на самой ссылке. VFS по-прежнему не держит учётных данных; `may_search` — это переданный вызывающим предикат над метаданными, которые VFS и так отдаёт, ровно как другие граничные проверки на этой странице.

`chmod` пишет ext2-inode и дополнительно записывает исторический per-process override для `stat`; `stat` предпочитает этот override (именно он держит синтетические узлы согласованными), а иначе сообщает реальные `VfsNode::mode`/`owner`. Создание через `open(O_CREAT)` и `mkdir` применяет к inode аргумент mode вызывающего, замаскированный umask, и проставляет эффективные ids создателя, поэтому процесс не-root владеет тем, что создал, и может это `chmod`-ить. Синтетические узлы не могут сохранять метаданные: их `set_mode` возвращает `NotSupported` (override всё равно заставляет `stat` сообщать mode), а `chown` возвращает `EPERM` вместо вида, будто владелец сохранён.

Установщик пакетов теперь применяет `mode` каждого tar-члена к созданному ext2-inode. Без этого каждая установленная через apt программа была бы `0644`, и проверка исполнения отвергала бы её даже для root.

### Сетевые сокеты: порт-гейт и `SOCK_RAW`

`bind(2)`/`listen(2)` на AF_INET-сокете обслуживает `arch/x86_64/linux/inet_sock.rs`
(`sys_bind_inet`/`sys_listen_inet`; диспетчер в `linux/mod.rs` различает AF_INET по
объекту fd, AF_UNIX остаётся на прежнем пути `unix_sock`). Решения — чистые предикаты
`cred.rs`, как и sticky-правило:

* `Creds::may_bind_port`: порт `< 1024` требует `CAP_NET_BIND_SERVICE`, сведённого к
  `euid == 0`; непривилегированный процесс получает `EACCES` (именно так отвечает
  Linux, а не `EPERM`). Порт `0` (эфемерный) и любой `>= 1024` доступны всем.
  Проверка идёт **до** обращения к стеку, поэтому отказ ничего не резервирует.
* `Creds::may_use_raw_socket`: `SOCK_RAW` только root; непривилегированному процессу —
  `EPERM`. Root получает `EOPNOTSUPP`: гейт допуска реализован, а пакетного уровня в
  ядре нет, и выдумывать полурабочий сокет нельзя.

`bind` резервирует порт в таблице собственного стека (TCP — созданием слушателя, UDP —
сменой порта), поэтому второй `bind` того же порта — `EADDRINUSE`, а не тихая
перезапись. Локальный адрес принимается только wildcard (`0.0.0.0`/`::`): у стека один
интерфейс, явный адрес — `EADDRNOTAVAIL`. Без сетевого устройства — `ENETDOWN`;
`listen(2)` на UDP — `EOPNOTSUPP`. Свойство P60 проверяет оба гейта против независимого
оракула, включая границу 1023/1024.

## 4. Что не реализовано (честные пробелы)

* **Нет логина и аутентификации.** Shell и все процессы, порождённые ядром, — root. Появилась минимальная база `/etc/passwd` + `/etc/group` и shell-команды `id`/`groups`/`su`, но `su` **не спрашивает пароль** и доступен только из root-сессии (фаза 1, см. `docs/security/groups.md`); login/getty/`/etc/shadow`/`sudo` отсутствуют. `su` per-сессионно меняет идентичность, с которой `lxrun` запускает Linux-программы, но встроенные команды shell остаются kernel-кодом с привилегиями ring 0.
* **Нет setuid/setgid-бинарников и повышения привилегий на exec.** `execve` сохраняет запись учётных данных; режим исполняемого файла не меняет ids.
* **Нет ACL, `fsuid`/`fsgid`, capabilities, seccomp, LSM, audit и namespaces.** Вся модель — owner/group/other (с дополнительными группами фазы 1) плюс обход для root. Логин/setuid-бинари/capabilities — дорожная карта фазы 2 в `docs/security/groups.md`.
* **Sticky-бит применяется только к родительскому каталогу записи.** `/tmp` — `0o1777`, и `unlink`/`rmdir`/`rename` разрешены лишь root'у, владельцу каталога и владельцу записи (`Creds::may_delete_child`, `EPERM`). Более тонких правил (`CAP_FOWNER` отдельно от root, sticky на не-каталогах, `renameat2` в стиле Linux с обменом) нет; `fb0`-эксклюзивность и ACL остаются соглашениями/пробелами.
* **AF_INET-сокеты: только `bind`/`listen`, без `accept`.** Слушатель создаётся уже в
  `bind` (порт резервируется там же), `listen` лишь помечает сокет и не меняет поведение
  стека; `accept(2)` на AF_INET не реализован (уходит в AF_UNIX-обработчик), `backlog`
  не моделируется, `getsockname` для AF_INET отсутствует. Пакетные raw-сокеты (raw IP,
  AF_PACKET, BPF-фильтры, promiscuous) не реализованы: есть только гейт допуска.
  Привязка к конкретному локальному адресу не поддерживается — только wildcard.
  `close(2)` снимает слушателя и освобождает порт, но **процесс, завершившийся без
  `close`**, оставляет занятый порт до перезагрузки: у слоя fd нет exit-свипа, а
  `impl Drop` на сокете потребовал бы брать `NET` под локом реестра compat (инвариант 4).
  Это ресурсный, а не привилегированный пробел: тот же процесс и так мог держать порт живым.
* **У синтетических узлов нет сохраняемого owner/mode.** `/dev` и `/proc` держат исторический per-process override для `stat`; файл не-root, созданный там, остаётся root-owned для целей `chmod`/`chown`. Ramfs `/tmp` — исключение: он хранит `mode`/`owner` с фазы 2.
* **Только SMEP.** `CR4.SMEP` выставляется, когда CPUID leaf 7 EBX bit 7 сообщает поддержку. SMAP (потребовал бы `stac`/`clac` вокруг каждого доступа к пользовательской памяти) и KPTI (потребовал бы отдельной иерархии таблиц страниц ядра) не реализованы.
* **`link(2)`/`symlink(2)` отсутствуют** в этом наборе сисколлов, поэтому правило родительского каталога задокументировано для операций VFS, которые использует установщик, а не проверяется через отсутствующий сисколл.
* **Образы, заполненные до этого изменения** (включая локальный `disk.img`), хранят установленные через apt программы как `0644`, потому что старый установщик игнорировал tar-mode. `execve` такого файла теперь возвращает `EACCES`, пока пакет не переустановят (установщик теперь применяет режим из архива) или файл не выполнят `chmod +x`. Внутренние лаунчеры ядра (`run_linux_binary`, harness'ы `lx_selftest`) не затронуты: они обходят проверку сисколлов, ровно как установщик пакетов обходит проверки VFS. Shell-овый `lxrun` сохраняет это поведение для root-сессии; из непривилегированной сессии (`su oleg`, `run_linux_binary_as`) путь разрешается **тем же** проверяющим обходчиком (`lookup_path_walk_checked` с `may_search` по креденшелам ребёнка) и дополнительно требует read+execute на финальном образе, поэтому search-биты промежуточных каталогов проверяются и здесь — как и в `execve(2)`, который загружает образ через тот же checked-обход. Непроверяемым остаётся только намеренно привилегированный kernel-лаунчер `run_linux_binary` (boot-selftest'ы), работающий как root.

## 5. Тесты

* **Host-свойства обходчика** (`host-tests/src/properties/link_walk_paths.rs`): `may_search` спрашивается перед каждым lookup — промежуточный каталог без `x` (включая `/` и каталоги, вставленные разыменованной ссылкой) даёт `AccessDenied`, а имя самого каталога без его собственного `x` по-прежнему резолвится. Это та же проверка, что применяет syscall-слой.
* **Host-свойство P59** (`host-tests/src/properties/p59.rs`): sticky-правило (`S_ISVTX`) против независимого оракула на произвольных ids/modes, инвариант «не-sticky каталог никогда не добавляет отказа» и конкретные сценарии `/tmp` 1777 (чужой файл нельзя, свой можно, root можно, группа не освобождает). Сначала тест был красным на заглушке, затем зелёным на реализации.
* **Host-свойство P56** (`host-tests/src/properties/p56.rs`): `may` против независимого оракула на произвольных ids/modes, точный закон root-execute, исчерпывающий выбор класса на малом множестве ids и инвариант владения для каждого перехода `set*id`. Запуск через `python3 tools/host_tests.py`.
* **Host-свойство P60** (`host-tests/src/properties/p60.rs`): порт-гейт `bind(2)`
  (`< 1024` — только root, граница 1023/1024, `0` и `>= 1024` — всем) и raw-гейт против
  независимого оракула; оба гейта независимы. RED на заглушке (`may_bind_port` без root,
  `may_use_raw_socket == true`), GREEN на реализации.
* **In-QEMU `e2e.py netperms`** (`tools/net_probe.c`): те же гейты на границе сисколлов из
  ring 3 с пользовательским `sockaddr_in` и подключённым NIC. root: bind :80/:8080 = 0,
  повторный bind :8080 = `EADDRINUSE`, `listen` = 0, `SOCK_RAW` = `EOPNOTSUPP`; после
  `su oleg` (uid 1000): bind :80 = `EACCES`, тот же сокет затем bind :8080 = 0 (отказ
  ничего не зарезервировал), `SOCK_RAW` = `EPERM`. После `close(2)` на слушателе порт
  снова свободен (`afterclose=0`): без этого фикса закрытый listener навсегда оставлял
  `EADDRINUSE`. Требуется `gcc`/`qemu-img`/`debugfs`.
* **In-QEMU `src/test.rs`** (`security_tests`, пять рутин): матрица прав, переходы setuid, правила chmod/chown плюс запись mode/owner в ext2, правило прав kill и круговой рейс get/set*id через сисколлы против синтетического `CompatState` (root сбрасывается в 1000/100, затем `setuid(0)`/`setgid(0)` дают `EPERM`). В сумме они не выделяют PMM-кадров, а ext2-тест использует heap-backed мок и удаляет свой файл.
* `python3 tools/e2e.py selftest` печатает `SELFTEST SUMMARY: 80 routines, 0 failed checks, 0 skipped`.

## 6. Чек-лист ревью для новых сисколлов

1. Добавьте номер в `abi::nr`, ветку `dispatch_supported` и `SUPPORTED_SYSCALLS` (и независимый литерал `EXPECTED`). Контракт поддержки — в `src/arch/x86_64/linux/abi.rs`.
2. Если сисколл трогает путь, решите, какой доступ нужен, и вызывайте те же хелперы (`check_node_access`, `check_dir_mutation`); не добавляйте проверку учётных данных внутрь реализации `VfsNode`.
3. Если он меняет учётные данные, идите через метод перехода `Creds` — никогда не мутируйте шесть ids по полям в обработчике.
4. Добавьте чистое решение в P56 (или соседнее свойство) и детерминированную in-QEMU рутину, когда замешано состояние ядра.
