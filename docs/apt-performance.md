# apt performance: phase timings, streaming `.deb`, transaction sync, index cache

Status: implementation notes and measured evidence for the `perf/apt-fast` work.
The behavior specification and the prior analysis are in
`/tmp/apt-fast-spec.md` (task brief), the reference-source comparison is against
apk-tools, pacman/libalpm and xbps.

The user-facing command is **`ppkg`** (renamed from `apt`; internal modules stay
`pkg::apt*`). User-visible log lines therefore start with `ppkg:` — the phase
timings below were captured before the rename in one live run (shown as `ppkg:`
in that raw evidence) and as `ppkg: timings` afterwards.

## What changed

| workstream | change | main code |
|---|---|---|
| W0 | Per-phase timers for every `ppkg update` / `ppkg install`, emitted as exactly one `ppkg: timings cmd=… <phase>=<ms>… total_ms=… heap_peak_kib=…` line (success and failure); totals exposed to the in-guest harness | `src/pkg/apt.rs` (`Timings`) |
| W1 | Two-pass streaming `.deb` install: pass 1 decompresses `data.tar` into a metadata-only plan, pass 2 decompresses again and writes each planned member as its bytes stream past. No full `Vec` for `data.tar`, no `Vec<TarEntry>` | `src/pkg/tar.rs` (`TarMeta`, `TarWalker`), `src/pkg/install.rs` (`plan_install_meta`), `src/pkg/install_fs.rs` (`StreamingInstall`), `src/pkg/apt.rs` |
| W2 | One `node.sync()` per install transaction (and once on the abort path) instead of after every package | `src/pkg/apt.rs` (`install_timed`) |
| W3 | Persistent compact index cache on ext2: keyed by the SHA-256 of the verified signed `Release` + suite/component/arch + format version; versioned, length-delimited, checksummed, fully validated; clean fallback | `src/pkg/apt_index.rs` (`to_compact_bytes`/`from_compact_bytes`), `src/pkg/apt.rs` (`store_index_cache`/`load_index_cache`) |

W4 (HTTP keep-alive, TLS session reuse, parallel downloads) is **not** implemented;
see "Remaining work" for the measured reason.

`ppkg install` also drives a DNF-style progress UI (total + per-package bars,
download/verify/unpack phases, known `[====    ]` and animated `<=>` unknown bars,
percent/speed/size/ETA, ≤10 FPS; ANSI multi-line on `--progress=ansi`, `\r`
single-line on the framebuffer, plain lines on serial/`--quiet`). Its pure renderer
is host-tested; see `src/shell/README.md`.

## Security invariants (unchanged)

* The signed `Release` is fetched and verified (OpenPGP chain, suite/architecture,
  `Date`/`Valid-Until`) before any index or `.deb` is used. The W3 cache is
  consulted **after** that verification and never replaces it; its key includes
  the SHA-256 of the verified Release body, so a mirror rollback/rotation or a
  configuration change is always a miss.
* Index bytes are checked against the signed size/SHA-256 before decompress/parse
  (cache hits are equivalent: the cache was produced from bytes that verified
  against the same Release, and the cache payload carries its own SHA-256).
* Every `.deb` is checked against the signed index SHA-256/size before `ar`
  parsing or decompression. The two-pass path performs that check before pass 1.
* Installer preflight stays atomic: `StreamingInstall::prepare` runs the
  F-x86n-1 (planner symlink descent), F-r2-vfs-1 (hardlink-alias), F-r3-vfs-1
  (resolved-spelling split) and F-r4-vfs-1 (pre-existing redirector) refusals
  **before the first inode**. Pass 2 can only write a member whose archive ordinal
  the plan accepted (`MetaOp::File.member`), so a stream that disagrees with the
  plan writes nothing unexpected.
* Caps: 64 MiB decompressed per `.deb` pass (`deb::MAX_DECOMPRESSED`), 512 MiB
  index stream (`deb::MAX_INDEX_STREAM_BYTES`), plus new metadata bounds
  `tar::STREAM_MAX_MEMBERS` and `tar::STREAM_MAX_EXTENSION` for the walker.
* No new `unsafe`. A `--no-default-features` build still refuses network access.

### Cache trust model (W3, explicit)

The cache lives under `/mnt/var/cache/pagh/apt/`, i.e. at the same trust level as
everything else installed there: packages are signature-verified before being
installed, and an actor who can rewrite `/mnt` can already rewrite the userland
and boot files this kernel executes. The cache checksum is an anti-corruption and
anti-clobbering measure, **not** an authentication replacement — the signed
Release check still gates every run, and the Release-digest key prevents stale or
mixed metadata. Any inconsistency (bad magic/version, foreign key, checksum
mismatch, undecodable payload, size over the cap) is a clean miss and the normal
verified network path runs.

## Measured results

Environment: QEMU/TCG (`qemu-system-x86_64 -cpu max`, 1 GiB RAM, 64 MiB virtio
disk), release kernel, local HTTP mirror on the host gateway. The benchmark
repository is generated by `tools/mini_repo.py bench` (signed by the deterministic
TEST key) with 5k/50k `Packages` stanzas and a three-package transaction whose
`data.tar`s decompress to 24 MiB / 192 files. All numbers are the kernel's own
`ppkg: timings` lines, so they include the same logging and scheduler costs in
both builds. TCG inflates CPU-bound phases and makes runs vary by roughly ±10%.

### Decision: two-pass vs temp-file spool (measured)

The alternative W1 design decompresses `data.tar` once into a temp file and reads
it back (once for planning, once for extraction). The in-guest probe measured the
same ext2/virtio path (`LXSELFTEST apt_bench spool probe_bytes=8388608 …`):

* sequential **write**: 160 ms / 8 MiB → 20 ms per MiB (24 MiB ≈ 0.48 s),
* sequential **read**: 1 930 ms / 8 MiB → 241 ms per MiB (24 MiB ≈ 5.8 s).

So a single spool round trip for the 24 MiB payload costs ≈6.3 s, versus
**≈3.0 s** for the second decompression pass of the two-pass design. On this
platform reads are ~12× more expensive than writes per byte, so the temp-file
variant is strictly worse even before the capacity problem: the spool (24 MiB)
and the installed output (24 MiB) must coexist on a 64 MiB partition, and a
`data.tar` near the 64 MiB decompression cap could never be spooled at all.
**Chosen: two-pass.** The measured install-time cost of the extra validation pass
is +27…36% under TCG; pass 2 itself (decompress + write) is 5–10% *faster* than
the baseline's `decompress_data` + `install` because it does not grow and copy
large `Vec`s. On hardware — where decompression is far cheaper relative to device
I/O than under TCG — the extra pass is proportionally much smaller; the memory
reduction is architecture-independent.

### W2 (sync) — honest note

`Ext2Fs::sync()` is a documented no-op: every mutation is already journaled and
checkpointed at `commit`, and the measured `sync_ms` is 0 in **both** builds. The
per-transaction change is therefore semantics-neutral today and produces no timing
win; it is the correct transaction boundary if sync ever becomes a real flush, and
it removes N−1 sync calls per transaction.

```bash
# signed benchmark repo + kernel-side benchmark (5k or 50k stanzas)
python3 tools/mini_repo.py bench /tmp/apt-bench --stanzas 5000 --size-mib 24
python3 tools/e2e.py bench --stanzas 5000 --size-mib 24            # boot 1
python3 tools/e2e.py bench --stanzas 5000 --size-mib 24 \
        --reuse-scratch-disk                                      # boot 2: cache hit

# the harness prints every ppkg: timings line and gates the install heap bound
# (--max-heap-kib; use 0 to measure a pre-W1 baseline without the bound)
```

### Live Debian `main` (`lx_livetest`, soft/network-dependent)

One run against `https://deb.debian.org/debian` (TCG, pre-rename log prefix):

```
apt: timings cmd=update release_fetch_ms=720 release_verify_ms=1755
    release_policy_ms=60 cache_load_ms=20 index_fetch_ms=9955 index_verify_ms=2340
    index_parse_ms=49780 cache_store_ms=0 pkgs=68825 total_ms=64635 heap_peak_kib=58411
LIVE_APT_UPDATE: count=68825
Resident_Index_Footprint = 26918148 bytes (26287 KiB)
```

The real full index (68 825 stanzas) parses for **49.8 s** and the whole update
takes 64.6 s on this emulated machine; the `busybox-static` `.deb` install was
still downloading when the soft timeout ended. This is exactly the case the W3
cache targets: with an unchanged `Release`, a later boot replaces fetch+verify+
parse (≈57 s) with the cache load, and no network/TLS work is done for the index at
all. It also shows why W4 (keep-alive/parallel) is secondary for the *index*: two
TLS fetches cost ≈12 s against ≈50 s of parsing.

## Tests added

* `host-tests/src/properties/tar_stream.rs` — `TarWalker` agreement with
  `read_tar` on every fixture (files, links, GNU `L`/`K`, ustar prefix, pax),
  every chunk boundary (1…whole), every truncated prefix, oversized extension,
  malformed pax, byte-level panic-freedom, and metadata-plan equivalence with the
  eager plan (operation order, deferred/unresolved hard links, all atomic-refusal
  counters and member ordinals).
* `host-tests/src/properties/apt_index_cache.rs` — compact index codec:
  lossless round-trip via the production streaming builder, owned/streaming
  equivalence, every truncation rejected, structural corruptions rejected
  (magic/version/lengths/`StrRef` ranges/trailing bytes), arbitrary byte flips
  never panic, 1 000-record ordinal consistency.
* `tools/e2e.py bench` + `src/selftest_lx.rs::run_apt_bench` — in-QEMU benchmark
  with correctness verification of the installed payload and the spool-cost probe.
* Existing F-x86n-1/F-r2-vfs-1/F-r3-vfs-1/F-r4-vfs-1 security tests still pass
  through the new streaming executor (`install_data_tar` is now a thin adapter
  over `StreamingInstall`), plus the full host suite and in-QEMU selftest.

## Remaining work / risks

1. **Install wall time +27…36% under TCG** (the mandatory preflight pass). Options,
   in order of expected value: (a) keep the eager in-memory path when a single
   bounded decode fits a small cap (e.g. ≤8 MiB) and stream only larger packages;
   (b) overlap pass 1 with the network fetch (W4 concurrency) so the validation
   pass is hidden behind the download; (c) accept it — the acceptance target is
   peak heap and small-RAM installability, and real hardware is far less
   CPU/decompression-bound than TCG.
2. **W4 network** is untouched. Local-mirror fetches are 45–60 ms for 84 KiB, so
   the local benchmark cannot justify keep-alive/parallel downloads. The live
   update path (Debian `main`, ~13 MiB `Packages.gz` over TLS) is where per-file
   TCP+TLS handshakes and serial downloads dominate; implement keep-alive + TLS
   session reuse + 2–4 parallel `.deb` fetches only after a live phase breakdown
   confirms it. Fail-closed TLS and signature checks must be preserved.
3. **Cache load is 4.9 s at 50k** versus 10.1 s parse (2.1×). Serializing the
   already-sorted `name_sorted`/`prov_sorted` tables (≈0.2 MiB extra) would skip
   `PackageIndexBuilder::finish` on load; worth doing if a live full-`main` load
   shows the sort dominating.
4. **Cache size**: 8.7 MiB for 50k stanzas; linear extrapolation to the full
   Debian `main` (~68k stanzas) is ≈12 MiB, which fits the 64 MiB disk. Boot 1
   pays the store (2.5 s at 50k); steady state (boot ≥2) is the 2.2× win. If the
   disk is full the store fails with a warning and the verified network path is
   used — never an update failure.
