# `ppkg install` и отзывчивость десктопа: курсор и часы панели

Этот документ фиксирует расследование жалобы «во время `ppkg install` замерзают
курсор и часы панели» и что именно исправлено. Проверка — живой QEMU (release),
реальный `ppkg install libc6` (три `.deb` из подписанного индекса Debian), при
работающем userspace-композиторе на `/dev/fb0`.

## Что измерено

Стенд: подготовленный desktop-ext2 (`/mnt/pd` = `pagh-desktop`,
`--backend fbdev --input evdev --clock now --frame-stats …`), композитор
припаркован `^Z` + `bg`, установка идёт в boot-shell, PS/2-мышь двигается каждые
~1.3 с, экран снимается через QEMU `screendump` (PPM), композитор сам пишет
посекундный `--frame-stats`.

| Утверждение | До | После |
|---|---|---|
| часы панели идут | **нет**: `clock_rect` побайтово одинаков во всех 15/15 сэмплах установки, пересекающей минуту | **да**: `07:16 → 07:17` внутри окна установки (28 px смены цифры) |
| курсор двигается во время install | да: каждый инжектированный сдвиг даёт курсор-размерный дифф (250 px), 37/37 сэмплов | да: 37/37 сэмплов, ни одной пары без диффа |
| композитор планируется | да (15–20 fps, ни одной секунды без кадра) | да (18–20 fps, ни одной секунды без кадра) |
| установка завершается | да (`total_ms≈48–56 с`) | да (`total_ms=50.6 с`, 3 пакета) |

Ключевой вывод: **это не голодание рендера**. Композитор всё время выдаёт кадры;
«замерзает» не отрисовка, а доставка ввода (и, отдельно, часы панели вообще не
перерисовывались).

## Причины (по слоям)

1. **Часы панели не обновлялись никогда.** `--clock now` один раз снимал
   `SystemTime` при старте; `Compositor::set_clock` больше не вызывался. `HH:MM`
   навсегда оставался минутой загрузки. Это не зависит от нагрузки.
2. **Блокирующий I/O в общем цикле.** Раз в секунду цикл кадра сам читал
   `/proc/net/dev` + четыре `SIOCGIF*`; `--frame-stats` показывал
   `gap_max_ms=60.0` на 93/95 секундах. Опрос вынесен в отдельный поток.
   Честно: на одном CPU та же работа всё равно конкурирует за процессор, поэтому
   измеренный `gap_max_ms` не уменьшился (75–82 мс раз в секунду). Это
   структурная правка (цикл кадра не делает I/O), а не выигрыш по задержке.
3. **PS/2-поток читался по одному байту на прерывание.** Общий выходной буфер
   8042 обслуживали два обработчика: IRQ1 забирал один байт клавиатуре, IRQ12 —
   один байт мыши. Пока распаковка держит прерывания замаскированными, это
   означает «один байт за окно», тогда как мышь ставит 3–4 байта каждые 10 мс;
   очередь 8042 (16 байт) в таком режиме может переполниться, и поток пакетов
   рвётся. Прямого A/B-подтверждения потери в QEMU получить не удалось (см.
   «Честные границы»): на этом стенде старый путь тоже доставлял каждый сдвиг,
   поэтому drain 8042 — устранение узкого места и страховка, а не измеренный
   выигрыш.

## Что исправлено

* `rust-apps/pagh-desktop`:
  * живые часы панели: раз в 500 мс пересчёт `HH:MM` и damage **только**
    `panel::clock_rect`; RTC из кадра не читается (`CLOCK_REALTIME` в Pagh —
    port-I/O к CMOS; первый вариант с `clock_now()` в цикле сам давал ~80 мс
    паузы дважды в секунду), часы идут от снимка `SystemTime` + `Instant`
    (`demo::format_unix`, host-тест);
  * сетевой опрос вынесен из цикла кадра в поток;
  * `--frame-stats PATH`: строка в секунду (включая `frames=0`) с
    `frames/avg/p95/max/gap_max_ms/damage/ev/ptr` + `summary`; `ev`/`ptr` —
    снимок ввода, чтобы отличать «не рисовали» от «ввод не дошёл». Заодно
    закрыт неограниченный рост выборки при дефолтном `--frame-log-every 0`.
* `src/drivers`:
  * `i8042::irq_drain()` — единый читатель байтового потока: выгребает **все**
    готовые байты за заход и маршрутизирует каждый по AUXDATA (мышь →
    `inputd::push_aux`, клавиатура → `ps2_kbd::handle_byte`, трекинг `^C/^Z`
    сохранён); спинлок делает пару «статус → данные» атомарной относительно
    второго читателя;
  * `inputd` вызывает `i8042::poll()` раз в тик — страховка на случай, когда
    IRQ12 задержан надолго: поток `inputd` под нагрузкой исполняется (он же
    диспетчеризует байты), поэтому порт не стоит полным;
  * `scheduler::cooperative_checkpoint()` после экст2-транзакций и на границе
    256 КиБ scan/extract `.deb` (уступка CPU, если есть готовая задача);
  * watchdog больше не считает законный `nanosleep` «застрявшим сисколлом»
    (refresh in-flight записи раз в 100 тиков).

## Воспроизведение

```sh
# в worktree с собранным ядром и статическим pagh-desktop:
REINJECT=1 python3 .cache/pagh-agent-notes/qbug1-live/repro.py \
    --prefix qbug1-final4 --package libc6 \
    --frame-stats /mnt/framestats-final4.txt --align-clock --sample-every 0.7
python3 .cache/pagh-agent-notes/qbug1-live/analyze.py qbug1-final4
```

## Честные границы

* «Замерзание курсора» в QEMU **не воспроизвелось**: и до, и после фикса
  каждый инжектированный сдвиг мыши давал курсор-размерный дифф (37/37 пар
  кадров), кадры шли 14–20 fps. Воспроизводится и исправлено другое —
  панельные часы вообще не перерисовывались. Приёмочный критерий «курсор
  двигается во время install» выполнен и подтверждён, но как *свойство текущего
  дерева*, а не как дельта этого PR. Drain 8042 остаётся hardening-правкой:
  она убирает чтение «один байт на IRQ» и добавляет опрос из `inputd`.
* Первая версия анализа сэмплов сравнивала не те пары кадров и дала ложный вывод
  «курсор не двигается»; исправленная попарная проверка это отменила. В отчёте
  оставлены только проверенные числа.
* Точный путь «окно — это kernel-shell» (`feat/term-full-shell-live`) на `dev`
  недоступен: там `ppkg` из десктопа не запускается, поэтому сценарий снят в
  boot-shell при живом композиторе.
* `gap_max_ms` включает нормальный темп кадров: при `--full-render` кадр
  ~22–28 мс, поэтому «хороший» gap — это интервал кадров, а не 16 мс.
