# `src/security/` — security-sensitive примитивы

Узкие API вокруг чувствительных операций. Сейчас — аппаратная энтропия и микшер
для `AT_RANDOM`-фоллбэка (issue #16).

## Файлы

| Файл | Роль |
|---|---|
| `mod.rs` | Корень: `pub mod entropy; pub mod seed;` |
| `entropy.rs` | Аппаратная энтропия x86_64 (RDSEED → RDRAND, fail-closed) **плюс** эффектная половина `AT_RANDOM`-фоллбэка: сбор boot-seed, счётчик, предупреждение о деградации (`mixed_fill`) |
| `seed.rs` | **Чистый** (core + `sha2`, без I/O и глобалов) микшер: `SeedPool` (SHA-256-транскрипт источников), `Observables`, `derive_bytes` — тот же код гоняют host-свойства P51 |

## Ключевые символы

- `EntropyError::Unavailable`
- `is_available() -> bool` — CPUID: leaf 1 ECX bit 30 (RDRAND), leaf 7 EBX bit 18 (RDSEED)
- `secure_u64() -> Result<u64, EntropyError>`
- `fill(dest: &mut [u8]) -> Result<(), EntropyError>` (LE-заполнение u64, хвост по частичному слову)
- `report_capabilities()` — boot-probe: печатает предупреждение о деградации, только
  если аппаратной энтропии нет (иначе — no-op, лог не меняется)
- `mixed_fill(dest: &mut [u8])` — единственный потребитель boot-seed; **не** участвует
  в `secure_u64`/`fill`
- `seed::{SeedPool, Observables, derive_bytes}` — микшер (host-тестируемый)

## Как работает

CPUID-проба возможностей; `rdseed_word`/`rdrand_word` — `#[target_feature]`-обёртки над
`_rdseed64_step`/`_rdrand64_step` с ретраями до 128 раз + `spin_loop()` между попытками
(на текущем тулчейне сами интринсики safe — лишние `unsafe`-блоки убраны, CPUID-предусловие
несёт `#[target_feature]`).

**Основной API fail-closed по дизайну**: никогда не подставляет таймстампы или PRNG;
`EntropyError::Unavailable` обязан прокидываться вызывающим. Это относится и к
`sys_getrandom` (EAGAIN), и к `net::tls::KernelRng`.

### `AT_RANDOM`: почему здесь исключение (issue #16)

ELF-блок `AT_RANDOM` (ключи stack-canary / pointer-mangling для glibc) читается
безусловно при старте процесса, поэтому «отказаться выдавать» его нельзя — это отказ
стартовать процесс. Старая реализация в этом случае отдавала 64-битный **xorshift** над
тик-часами, RTC, pid и нулём (пятое слагаемое `secure_u64().unwrap_or(0)` на этом пути
всегда 0 — «free-running process-lifetime counter» из старого комментария не существовал):
линейный поток по наблюдаемым величинам, каждая канарейка предсказуема, а глобальное
состояние переносилось в следующий блок, так что одного наблюдения хватало на всю
последовательность. Гарантии «блок никогда не ноль» тоже не было — ноль достижим при
конкретных тиках.

Теперь при отсутствии RDSEED/RDRAND блок выводится из **смешанного boot-seed**:

- `collect_boot_seed()` собирает источники: джиттер TSC (XOR-свёртка дельт между
  подряд идущими `RDTSC` — на голом железе от прерываний/кэша/SMT, под QEMU/TCG от
  планировщика хоста), латентность/гонки чтений CMOS RTC, счётчики ядра (тики,
  current/next pid, кадры PMM, учёт кучи) и layout адресного пространства (CR3, адреса
  объектов). **Энтропию несут ТОЛЬКО тайминговые источники** (джиттер TSC и
  латентности/гонки RTC): счётчики и layout наблюдаемы или фиксированы конфигурацией —
  измерение верификатора t11 показало их константными на всех 5 прогонах (0 бит), тогда
  как латентности RTC давали десятки бит, а счётчик итераций джиттера ≈8.5 бита. **Не**
  используется неинициализированная память (это не sound Rust);
- `SeedPool` сворачивает всё в 32-байтный seed через SHA-256 (метки + длины, чтобы не
  было склейки);
- `derive_bytes(seed, counter, observables)` даёт блок; `counter` монотонно растёт, поэтому
  два процесса с **одинаковыми** публичными входами (тики/RTC/pid) получают разные блоки;
- деградация **объявляется**: один `warn!` при загрузке (boot-probe) или на первом
  использовании — `entropy: stage=degraded cause=NoHardwareEntropy cpu=…`.

**Честная граница**: это best-effort, НЕ CSPRNG. Секретность даёт ТОЛЬКО тайминговый
джиттер (TSC + латентности RTC) — счётчики и layout энтропии не добавляют; на идеально детерминированном
replay seed воспроизводим — поэтому деградация видна в логе, поэтому `sys_getrandom`
по-прежнему fail-closed, и именно поэтому `-cpu max` (RDSEED/RDRAND) остаётся
рекомендуемой конфигурацией. Доказательства: host-свойства P51 (`seed` напрямую:
лавинность с порогом, разделение секретов, атака-модель по публичным входам, реакция на
выпадение одного входа) + in-QEMU проверка `selftest` (64 блока: не повторы, не
вырожденные, digest в лог) на `-cpu qemu64` и на `-cpu max`.

## Зависимости

- **От:** `core::arch::x86_64`, `sha2` (только `seed.rs`), `sync::spinlock`,
  `task::scheduler`, `memory::{pmm, heap, vmm}`, `arch::x86_64::linux::rtc`.
- **На неё:** `net::tls::KernelRng` — адаптер к `rand_core::RngCore + CryptoRng`
  для embedded-tls: ключи TLS-сессий отсюда; `arch::x86_64::linux::misc::random_bytes_16`
  (AT_RANDOM); host-свойства P51.

## Замечания

- RDSEED/RDRAND-бэкенд не компенсирует отсутствия аутентификации пира в TLS: ключи
  сессии случайны и fail-closed, но доверие к серверу даёт только верификатор
  (`net::tls` → `tls_auth`/`tls_chain`/`ca_bundle`), и он ограничен пиннутыми корнями.
  Подписи метаданных Debian и digest'ы пакетов не проверяются (`SECURITY.md`).
- Транзиентный сбой инструкции после успешной проверки доступности трактуется как
  нарушение инварианта, а не повод подставить предсказуемые байты.
- `mixed_fill` — единственное место, где байты boot-seed покидают модуль; всё, что
  запрашивает криптографическую случайность (`fill`, TLS-ключи, `getrandom`), этих
  байтов не получает.
